# 상품 등록 정보 정확성 수정 (2026-08-10)

스마트스토어에 상품을 올릴 때 들어가는 정보 중 상당수가 **실제 값이 아니라 고정값이나 추측값**으로 나가고 있었다. 코드만 보고는 몰랐고, 이미 등록된 상품 2건을 커머스 API로 직접 조회해 화면에 실제로 저장된 값과 대조하면서 드러났다.

이 문서는 무엇이 잘못돼 있었고 어떻게 고쳤는지를 기록한다.

## 1. 원산지가 상품과 무관하게 등록되던 문제

### 무엇이 문제였나

원산지 코드를 `03`으로 고정해놓고, 코드 주석에는 "국내산으로 확인된 경우에만 03(국산)을 쓴다"고 적혀 있었다. 그래서 국내산인지 검사하는 로직까지 붙어 있었다.

그런데 네이버 원산지 코드표를 실제로 조회해보니 **`03`은 국산이 아니라 "상세설명에 표시"** 였다. 국산은 `00`, 수입산은 `02` 하위 코드다.

즉 국내산 여부를 검사하는 로직은 돌고 있었지만, 정작 등록되는 값은 원산지와 아무 상관이 없었다. 그리고 "상세설명에 표시"를 선택했으면 상세설명에 원산지가 실제로 적혀 있어야 하는데, 그걸 보장하는 코드는 어디에도 없었다.

원산지 표시는 법으로 정해진 의무 사항이라 잘못 표시하면 제재 대상이 된다.

### 어떻게 고쳤나

네이버가 원산지 코드표를 API로 제공한다는 걸 확인했다(535건).

```
GET /external/v1/product-origin-areas
```

그리고 도매매가 원산지를 정확하게 준다. 발가락양말의 경우 `수입산_아시아_중국`이다. 네이버 코드표의 `수입산:아시아>중국`(코드 `0200037`)과 **구분자만 다르다.**

그래서 도매매 표기를 네이버 형식으로 변환해서 정확한 코드를 찾도록 했다.

```
수입산_아시아_중국  →  수입산:아시아>중국  →  0200037
국산_경기도_이천시  →  국산:경기도>이천시  →  0002500
```

하위 지역이 코드표에 없으면 상위로 한 단계씩 올라가며 재시도한다(`수입산_아시아_중국_광둥성`이 없으면 `수입산_아시아_중국`으로). **끝까지 못 찾으면 등록을 막는다** — 추측값으로 밀어넣지 않는다.

신규 모듈: `bebrave/smartstore/origin.py`

## 2. 상품정보제공고시가 전 상품 "기타"였던 문제

### 무엇이 문제였나

전자상거래법상 상품마다 고시해야 할 정보가 정해져 있고, 품목에 따라 항목이 다르다. 의류면 소재·치수·세탁방법, 주방용품이면 재질·구성품·제조국 같은 식이다.

그런데 모든 상품을 `ETC`(기타 재화) 하나로 등록하고 있었다. 게다가 그 "기타" 유형조차 **필수 항목 6개 중 4개만** 채우고 있어서, 법에 의한 인증 사항과 A/S 책임자가 빠진 채로 등록됐다.

### 어떻게 고쳤나

네이버가 **36개 고시유형별로 어떤 항목을 채워야 하는지 스펙을 통째로 내려준다**는 걸 발견했다.

```
GET /external/v1/products-for-provided-notice
```

응답에 유형마다 `fieldName`, `fieldDescription`, `fieldType`, `fieldMaxLength`가 들어 있다. 그래서 항목 목록을 하드코딩하지 않고 **받아서 자동으로 채우게** 했다. 유형이 늘거나 항목이 바뀌어도 코드를 고칠 필요가 없다.

유형은 카테고리 경로로 결정한다.

```
패션잡화>양말>여성양말>덧신   →  WEAR (의류)
주방용품>조리도구>주걱        →  KITCHEN_UTENSILS (주방용품)
패션잡화>패션소품>우산        →  FASHION_ITEMS (패션잡화)
확신이 없는 경우              →  ETC (기타 재화)
```

값은 도매매에서 찾을 수 있는 것(제조사·제조국·모델명)을 우선 쓰고, 찾을 수 없는 항목은 `상세페이지 참조`로 채운다. 빈 값으로 두면 등록이 거부되기 때문이다.

**제조연월·유통기한·수입신고 여부 같은 날짜·불리언 항목은 일부러 생략했다.** 도매매가 주지 않는 정보를 지어내면 허위 표시가 되기 때문이다.

신규 모듈: `bebrave/smartstore/notice.py`

## 3. 제조사에 공급사 ID가 들어가던 문제

### 무엇이 문제였나

등록된 상품의 제조사 항목에 `seoul7rsoe`가 들어가 있었다. 이건 제조사명이 아니라 도매매 공급사의 내부 아이디다. 소비자에게 그대로 보인다.

모델명에는 도매매 상품번호가 들어가 있었다.

### 어떻게 고쳤나

도매매 상품 상세를 확인해보니 **제조사와 모델명을 별도 필드로 주고 있었다.** 발가락양말의 경우 제조사가 `(주)엘앤디`다. 이 필드를 아예 읽지 않고 있었던 게 원인이다.

이제 실제 값을 쓴다. 다만 도매매가 `해당없음`, `없음`, `-` 같은 문자열로 "값 없음"을 표현하는 경우가 있어서, 이런 자리표시자는 걸러내고 대체값을 쓴다.

## 4·5. 품절과 도매가 변동을 감지하지 못하던 문제

### 무엇이 문제였나

등록할 때 재고를 정하고 그 뒤로는 아무도 확인하지 않았다. 등록된 상품 2건 모두 재고가 999로 박혀 있었다.

**도매매에서 품절돼도 우리 스토어는 계속 판매중이다.** 주문을 받고 나서야 발주가 안 되는 걸 알게 되고, 그러면 발송 지연이나 판매자 귀책 취소가 된다. 굿서비스 점수가 깎이는 경로다. 위탁판매에서 계정이 망가지는 가장 흔한 원인이다.

도매가도 마찬가지다. 도매가 890원 기준으로 판매가 6,600원을 정했는데, 공급사가 도매가를 올리면 마진이 무너지는 걸 알 방법이 없었다.

### 어떻게 고쳤나

등록 상품을 도매매와 대조하는 명령을 만들었다.

```bash
python3 main.py sync           # 미리보기 (반영 안 함)
python3 main.py sync --apply   # 실제 반영
```

판정 규칙:

- **품절이거나 도매매에서 상품이 사라짐** → 즉시 판매중지
- **재고가 등록값보다 적음** → 그 수량으로 조정
- **도매가가 올라 최소 마진 미달** → 경고만. 판매가 인상은 검색 노출 순위에 영향을 주므로 사람이 판단할 일이라 자동으로 올리지 않는다.

여기서 확인한 중요한 제약이 하나 있다. **네이버 상품 수정 API는 부분 갱신을 지원하지 않는다.** 요청에 포함하지 않은 항목은 삭제된다. 그래서 재고 하나만 바꾸려 해도 현재 상태를 조회해서 그 위에 수정을 얹어 통째로 다시 보내야 한다. 이 패턴을 공통 함수로 빼고 기존 판매중지 전환 로직도 여기에 합쳤다.

신규 모듈: `bebrave/smartstore/sync.py`

## 6. 상세페이지 사진이 도매매 서버를 가리키던 문제

### 무엇이 문제였나

등록된 상품의 상세설명을 열어보니 사진 3장이 전부 `cdn1.domeggook.com` 주소였다. **공급사가 상품을 내리면 우리 상세페이지 사진이 통째로 사라진다.**

대표 이미지와 추가 이미지는 네이버 서버로 옮기고 있었는데, 상세설명 안의 사진은 빠져 있었다. 원인은 순서였다. 상세설명을 먼저 만들고 이미지 업로드를 나중에 해서, 주소를 바꿔칠 시점이 없었다.

### 어떻게 고쳤나

이미지 업로드를 상세설명 생성보다 **앞으로** 옮겼다. 먼저 사진을 전부 네이버 서버로 올리고, 옛 주소와 새 주소의 대응표를 만들어 상세설명 HTML의 주소를 바꾼 뒤, 그 상태로 상세설명을 만든다.

미리보기(dry-run)에서는 실제 업로드를 하지 않으므로 도매매 주소가 그대로 보인다. 이건 의도한 동작이다.

## 의도적으로 손대지 않은 것

**고객센터·A/S 전화번호가 `010-0000-0000` 더미값으로 나가고 있다.** 상품정보제공고시 필수 항목이라 소비자에게 그대로 보이고, 가짜 번호는 고시 위반 소지가 있다.

이번에는 일부러 고치지 않았다. 1인 사업자가 개인 번호를 노출할지, 별도 번호를 쓸지, 보통 어떻게 처리하는지 확인한 뒤 정하기로 했기 때문이다. 코드에 `TODO(#1)` 표시를 남겨뒀고, 값이 한 곳(`notice.py`의 `CS_PHONE_NUMBER`)에 모여 있어서 나중에 한 줄만 고치면 된다.

**판매 개시 전에 반드시 처리해야 한다.**

## 아직 검증되지 않은 것

이번 수정은 **미리보기와 단위 테스트까지만** 통과한 상태다. 실제로 상품을 등록해서 네이버가 받아주는지는 확인하지 않았다.

실전에서 갈릴 수 있는 것들:

- 수입산일 때 수입사(importer) 정보가 필수인지
- 고시유형의 하위 노드 이름(`wear`, `kitchenUtensils`)이 맞는지
- 날짜·불리언 항목을 생략해도 등록이 되는지
- 상세설명 안의 이미지가 네이버 주소로 저장되는지

판매중지 상태로 1건 등록한 뒤 커머스 API로 조회해 대조하면 확인된다. **대분류는 등록 후 변경이 불가능하므로 카테고리를 먼저 확인하고 진행할 것.**

## 다른 환경에서 확인하는 방법

```bash
git pull

# 1) 테스트 — 원산지 매핑, 고시 항목 채우기, 동기화 판정
python3 -m bebrave.smartstore.test_origin
python3 -m bebrave.smartstore.test_notice
python3 -m bebrave.smartstore.test_sync

# 2) 등록 상품을 도매매와 대조 (읽기만, 반영 안 함)
python3 main.py sync

# 3) 등록 바디 미리보기 — 원산지 코드와 고시유형이 채워지는지 확인
python3 main.py register --keyword "발가락양말" --dry-run --force
```

`.env`에 `NAVER_COMMERCE_CLIENT_ID` / `NAVER_COMMERCE_CLIENT_SECRET` / `DOMEMAE_API_KEY`가 필요하다. 커머스 API는 IP 허용목록 방식이라 다른 환경에서는 **커머스API센터에 그 환경의 공인 IP를 등록**해야 한다. `GW.IP_NOT_ALLOWED` 오류가 나면 코드 문제가 아니라 이것이다.

원산지 코드표와 고시 스펙은 첫 실행 시 API로 받아 `data/`에 캐시한다(각각 30일). 캐시 파일은 재생성 가능해서 저장소에 포함하지 않았다.

## 곁다리로 확인된 것

**환경설정을 명령마다 따로 읽는 구조가 실제로 문제를 일으켰다.** `sync` 명령을 추가했더니 `.env`를 못 읽어서 도매매 조회가 전부 실패했다. 우선 맞춰뒀지만 근본 수정은 별도 항목으로 남아 있다.

**품질 게이트는 제대로 작동한다.** 발굴 1순위인 발가락양말이 상세설명 179자, 대표이미지 760px로 자동 차단됐다. 다만 1순위 후보가 부실 리스팅이라는 건 소싱 쪽에서 따로 볼 문제일 수 있다.
