## 2. 배경 — 왜 재설계하나

기능을 하나씩 추가할 때마다 메뉴를 하나씩 늘린 결과, 사이드바가 **16개 항목**까지 불어났다. 특히 상품 5종(발굴후보 제외 4개)과 주문 3종은 **같은 대상(상품 한 줄 / 주문 한 건)을 서로 다른 시점에 만든 화면이 각자 따로 보여주는 구조**라 역할이 겹친다. `발주 대기열` 한 화면 안에서도 구역 4개가 항상 세로로 다 펼쳐져 있어 "지금 뭘 해야 하는지"가 안 보인다는 피드백을 받음.

## 3. 리서치 근거 (2026-08-28 조사)

- **Shopify Polaris** ([navigation](https://shopify.dev/docs/apps/design/navigation), [Tabs](https://polaris-react.shopify.com/components/navigation/tabs), [Index filters](https://polaris-react.shopify.com/components/selection-and-input/index-filters)): 탭은 "같은 콘텐츠를 다르게 필터링한 것"에만 쓴다. Index table + Index filters 패턴 — 탭 하나하나가 같은 데이터셋의 "저장된 뷰"다. 탭 안에서 작업이 끝나야 하고, 탭을 오가며 하나의 작업을 완성시키면 안 된다. 사이드바는 7개 항목이 기준.
- **Nielsen Norman Group**: Progressive disclosure(요약→맥락→상세 3단계)로 인지부하 최대 55% 감소.
- **네이버 스마트스토어센터 자체 IA**: 최상위 6개 그룹(상품관리/판매관리/정산관리/문의리뷰관리/스토어관리/판매자정보)뿐. 사용자가 매일 쓰는 익숙한 기준점.

공통 결론: **"대상(무엇을 보는가)" 기준으로 페이지를 만들고, "시점/상태"는 그 안의 탭으로 처리한다.**

## 4. 현재 구조 진단 (겹치는 지점)

**상품 4종** — 전부 "등록된 상품 한 줄"에 대한 다른 정보 조각:
| 화면(route) | 하는 일 |
|---|---|
| 등록 상품 (`/registered`) | 등록 스냅샷(이름/가격/마진) + 상태 캐시 |
| 재고·가격 동기화 (`/sync`) | 도매매 실시간 대조 → 품절·마진경고 판정 (`bebrave/smartstore/sync.py`) |
| 판매추적 (`/tracker`) | 최근판매일 3개월/13개월 위험 판정 + 수동추가 폼 (`bebrave/tracker/products.py`) — `판매성과`가 더 정확한 근거로 이미 대체함 |
| 판매 성과 (`/performance`) | 주문/매출/순수익 + 무판매진단 + 품질점수 + 액션 (`bebrave/report/performance.py`, `bebrave/smartstore/listing_quality.py`) — 가장 완성도 높음 |

**주문 3종** — 전부 "결제완료 주문 → 발주·발송 처리" 흐름의 다른 상태:
| 화면(route) | 하는 일 |
|---|---|
| 주문 확인 (`/orders`) | 최근 N시간 조회 + 인라인 발송폼(이름매칭 기반, 구버전) |
| 발주 대기열 (`/purchase/queue`) | 확정매칭 큐 + 가드 + 일괄발주 + 발송처리 (`bebrave/smartstore/purchase_queue.py`) — 상위호환 |
| 수동 발주 (`/purchase`) | 매칭실패 건 단건 입력 폼 |

정산 3종(`/settlement`, `/reconcile`, `/cashflow`)과 CS 내부 2섹션(반품/문의, `/cs`)은 이미 같은 대상을 보는 화면이라 탭 전환만 하면 됨(로직 변경 없음).

## 5. 확정된 목표 구조 — 16개 메뉴 → 7개

```
홈 (헬스체크 흡수)                                    ← 확정: 합치기
발굴 후보                                             ← 그대로
상품 관리   [전체 | 조치 필요 | 정상판매중]              ← 등록상품+재고동기화+판매추적+판매성과 통합
주문·발주   [처리할 주문 | 발송 대기 | 수동 발주 | 전체 이력]  ← 주문확인+발주대기열+수동발주 통합
CS         [반품·취소 | 상품문의]                       ← 탭화만
정산       [캘린더 | 대사 | 현금흐름]                    ← 탭화만
도구       [주간리포트 | 마진계산]
```

### 상품 관리 (가장 큰 작업)
하나의 표, 컬럼: `상품명 | 판매가 | 재고상태 | 주문건수 | 매출 | 순수익 | 진단점수 | 상태`. 탭은 같은 표의 필터만 다름(전체/조치필요/정상판매중). 기존 액션(이름 재최적화·판매중지·가격변경·실시간 상태확인)은 각 행 유지. `판매추적`의 13개월 자동삭제 위험 판정만 상태 배지 세 번째 단계로 흡수하고, 나머지(수동추가 폼, 이름매칭 동기화 버튼)는 폐기.

**확정: 도매매 재고는 캐시 + "지금 확인" 갱신 버튼 방식.** 방문마다 실시간 조회하지 않음(기존 `/registered` 페이지의 상태캐시 패턴 재사용, `PRODUCT_STATUS_CACHE` 참고). 상품 늘어나도 페이지 안 느려짐.

### 주문·발주
지금 `발주 대기열`에 항상 다 펼쳐진 이머니배너/바로발주/보류/처리완료를 탭으로 분리(Progressive disclosure 적용). "처리할 주문" 탭이 기본, 보류 건이 있으면 배지로 표시. 보류 항목은 가능하면 탭 이동 없이 그 자리에서 수동입력 폼으로 전환(최소 JS 필요 — 아래 구현방식 참고). "전체 이력"이 구 주문확인의 축소된 역할(디버깅/과거조회용).

## 6. 구현 방식
Flask + Jinja, JS 프레임워크 없음(모달만 바닐라 JS 있음, `base.html` 참고).
- **기본**: 쿼리파라미터 탭(`?tab=ready`) — 서버가 해당 탭만 렌더링. `index.html`/`settlement.html`의 월 이동 네비게이션이 이미 이 패턴이라 그대로 재사용.
- **예외**: 주문·발주의 "보류 → 그 자리에서 수동입력" 같은 상호작용만 최소 클라이언트 JS로 처리.
- CS/정산/도구 탭화는 로직 변경 없이 껍데기만 씌우는 작업이라 가장 안전 — 파일럿으로 먼저 진행 권장.
