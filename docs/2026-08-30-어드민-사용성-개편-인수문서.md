## 1. 배경 — 왜 이걸 하나

메뉴는 16개 → 7개로 줄였지만 **화면 안쪽은 그대로**였다. 그래서 "메뉴는 찾기 쉬운데 들어가면 뭘 해야 할지 모르겠다"가 됐다.

사용자 원문:

> "전체적으로 내가 들어갔을때 뭘해야하는지가 한눈에 안들어와. 상품관리 들어가면 상태 컬럼에 내용이 초기에 너무 많이 노출되어있어서 보기 힘들어. 하단 회색 텍스트들은 툴팁이나 다른식으로 풀어서 필요할때 볼 수 있게. 최우측 버튼(액션)영역도 버튼 크기도 제각각, 그리고 각각이 뭘 의미하는건지. 상품관리 메뉴 자체가 의도가 상품을 관리하는건데 개별로 관리하는 것 밖에 없어서 일괄(체크 후) 관리가 안되는것도 그렇고. 중요한건 사용성 관점에서 사용하기 좋은 시스템이 되었으면해, 내가 헷갈리지 않도록."

근본 원인: **모든 화면이 "데이터가 뭔가"에 답하고 "지금 뭘 해야 하나"에는 답하지 않는다.**

### 발견 1 — 정보 위계가 뒤집혀 있다 ★

등록 상품 2개가 **둘 다 네이버에서 SUSPENSION(판매중지)** 상태다. 스토어에서 살 수 있는 게 하나도 없고, 매출 0원의 진짜 원인이다.

그런데 화면은:

```
재고상태:  [이상없음]  ← 큰 초록 배지 (도매매 재고 기준)
           재고 3,432,752개, 도매가 3,190원      ← 회색
           네이버 SUSPENSION · 재고 999개        ← 회색, 가장 작게  ★진짜 원인
```

**"팔 수 없는 상태"가 회색으로 묻히고 "도매 재고 있음"이 초록 배지로 승격돼 있다.**

### 발견 2 — 소싱 2트랙이 저장 단계에서 사라진다 ★

소싱은 원래 2트랙이고 **백엔드에 이미 구현돼 있다**(`bebrave/sourcing/discover.py`, `config.py`). 터미널 리포트(`main.py sourcing`)는 섹션을 나눠 출력한다.

- **트랙 A (신규 틈새)** — 경쟁 적은 블루오션. 상품명만 다듬어 **바로 등록**
- **트랙 B (리메이크)** — 이미 풀린 시장이지만 상품명·상세이미지를 **다시 만들면 이길 여지**가 있음

점수 가중치도 합격선도 다르다(A: 진입가능성 45%·55점 / B: 수요 45%·60점). **해야 하는 일의 양이 완전히 다르다.**

그런데 `to_product_candidates()`(discover.py:576)가 `track`·`recommendation`을 복사하지 않는다:

| 문제 | 실측 |
|---|---|
| 트랙 정보 소실 | 저장된 294건 **전부 트랙 없음** |
| 리메이크 후보가 조용히 삭제됨 | 중복 제거를 키워드만으로 함(app.py `discover_scan`) → 같은 키워드가 두 트랙에 다 뜨면 먼저 도는 A만 남고 B는 버려짐 |
| 수요 크기 소실 | 광고 API 실측 월검색수를 저장 시 **0으로 덮어씀** → 294건 전부 0 |

**화면 문제가 아니라 데이터가 안 남는 문제다.** 화면부터 고치면 안 된다.

> 참고: `product_count`는 네이버쇼핑 API 종료(2026-07-31)로 조회 자체가 불가해 전부 0이고, 그래서 골든레이시오가 전부 `inf`다. **이건 코드로 못 고친다** — 알려진 제약이며 이번 범위 밖.

## 2. 설계 원칙

- **한 화면 = 하나의 질문.** 홈="오늘 뭐부터?", 헬스체크="내 스토어 괜찮나?", 상품="어떤 상품을 손봐야 하나?"
- **행위가 다르면 구분한다** ★ — 같은 목록이라도 요구되는 작업이 다르면(클릭 한 번 vs 반나절 리메이크, 조회 전용 vs 실제 변경) 탭이나 그룹으로 갈라놓는다. 데이터 종류가 아니라 **할 일의 종류**로 나눈다. (사용자가 직접 제시한 관점)
- **위계 = 결과의 무게.** 팔 수 없는 상태 > 도매 재고. 되돌리기 어려운 버튼 > 조회 버튼.
- **모든 숫자에는 목적지가 있다.** 클릭 안 되는 숫자는 링크를 붙이거나 뺀다.
- **행에는 판단 근거만, 상세는 요청 시.**
- **불확실한 추정은 그렇다고 말한다.** 원인 분석엔 "추정" 표시 + 근거 수치 동반.
- 기존 것 재사용 우선. 새 의존성 0, 새 파일 최소.

### 1-2. 표 구조: 9컬럼 → 6컬럼

```
[☑] | 상품 | 판매가 | 성과 | 리스팅 품질(?) | 지금 할 일
```

- **상품 셀**: 상품명 + 상태 배지 + 조치 사유 한 줄. 그 아래 `<details><summary class="hint">상세 ▾</summary>`에 접힌 정보(도매가, 도매매 판정 상세, 이름변경 이력, 교체 후보). **네이티브 `<details>`** — JS 0줄, 키보드·접근성 무료.
- **성과 셀**: `td.num`으로 주문·매출·순수익 3줄.
- **툴팁 vs 확장행 규칙**: *행마다 값이 다른 것* = `<details>`. *컬럼의 정의·판정 기준* = `.tip-btn`(base.html에 이미 구현, candidates.html에서 쓰는 패턴). 헤더에 "리스팅 품질이 뭔지", "조치 필요 기준이 뭔지" 툴팁 신설.

### 1-4. "조치 필요"를 행위별 그룹으로 (사용자 제시 관점)

지금은 `조치 필요 2건` 한 덩어리인데 실제 필요한 작업이 4가지로 다르다:

| 그룹 | 해야 하는 일 | 성격 | 일괄 |
|---|---|---|---|
| 판매중지 상태 | 다시 팔지 판단 | 클릭 한 번 | ○ |
| 도매매 품절·재고변동 | 스토어에 반영 | 클릭 한 번, 되돌리기 번거로움 | ○ (게이트) |
| 마진 붕괴 | 가격을 얼마로 할지 **결정** | 사람 판단(노출순위 영향) | △ 권장가 일괄만 |
| 무판매 | 이름 고칠지 상품 교체할지 | 전략 판단, 오래 걸림 | △ 이름 재최적화만 |

→ `조치 필요` 탭 안에서 **그룹 헤더로 묶고 그룹마다 일괄 버튼.** 클릭 한 번 일과 반나절 고민할 일이 섞이면 우선순위를 못 정한다.

## 2단계 — 상품 일괄 관리

신규 `POST /products/bulk` → `products_bulk()`. **`purchase_bulk_place()`(app.py:1218)의 5단계 구조를 그대로 이식**:

1. `request.form.getlist()` → 액션별 상태 검증 필터
2. `live` 체크박스 **dry-run 게이트**
3. `token = get_access_token()` 루프 밖 1회 (실패 시 전체 중단)
4. 건별 `try/except` — 실패해도 계속, `failed` 누적
5. 집계 flash + 실패 시 `_notify()`

| 액션 | 대상 | 확인 게이트 | 재사용 |
|---|---|---|---|
| `apply_sync` | sync 캐시의 품절·재고조정 | **필수** | `sync.apply_result(SyncResult(**캐시dict), token)` — 도매매 재조회 없이 네이버 2회/건 |
| `suspend` | 선택 건 | **필수** | `update_registered_product` |
| `reoptimize` | 무판매 | **필수** (dry-run에 before→after 이름 나열) | `optimize_name` |
| `refresh_status` | 전체 | 불필요(읽기 전용) | `fetch_product_statuses` |

**성능 주의**: 기존 개별 액션은 건마다 `registered_products.json` 전체를 로드/덮어쓴다. 일괄에서는 **루프 밖 1회 로드 / 끝나고 1회 저장**, `PRODUCT_SYNC_CACHE.unlink()`도 **1회만**.

**참고 사실** (조사 완료):
- `update_registered_product()`는 건당 네이버 GET+PUT **2회**. 토큰을 인자로 받으므로 루프 밖 1회 획득 재사용 가능
- `get_access_token()`은 프로세스 전역 1시간 캐시 → 루프 안에서 불러도 재요청 없음
- `optimize_name()`은 **외부 API를 안 쓴다**(순수 로컬 정규식+사전). N건 반복해도 비용 0. 병목은 네이버 PUT뿐
- `sync_all(dry_run=False)`는 **전체 아니면 전무**라 선택 반영엔 부적합. `apply_result()`가 1건 단위라 이걸 루프 돌리는 게 맞다

**중복 제거**: `_apply_product_action(action, record, token, sync)` 헬퍼 하나를 만들고 기존 `performance_suspend`(1108)/`performance_reoptimize_name`(1128)/`sync_apply_price`(869) 본문을 이 헬퍼 호출로 축약. 안전 게이트는 라우트 층에 유지.

**삭제**: products.html 하단 "실제로 반영" 패널 + `/sync/apply`(846) — `apply_sync` 일괄이 상위호환.

**UI**: orders.html의 `.ready-check` + `#checkAll` 패턴 복사. 선택 0건이면 버튼 `disabled`.

## 3단계 — 홈 = 오늘 할 일

**할 일과 헬스체크를 완전히 분리한다.** 할 일은 홈으로, 거시 진단은 헬스체크 탭으로(4단계).

```
홈
[오늘 할 일] [헬스체크]
─────────────────────────────────────────
오늘 할 일  6건

  주문 처리  3건
    · 발주할 주문 2건 — 이머니 9,890원 필요       [주문·발주 →]
    · 발송할 주문 1건 — 송장 입력 대기            [발송 대기 →]

  상품 조치  2건
    · 판매중지 상태 2개 — 스토어에 노출 안 되는 중 [상품 관리 →]

  고객 응대  1건
    · 미답변 문의 1건                             [CS →]

  정산 확인  0건

이번 달   매출 · 순수익 · 주문 · 반품  (4개, 전부 클릭 가능)
▸ 매출 추이 (접기 가능)
▸ 연동 상태 (기본 닫힘)
```

- 카테고리는 **앉은 자리에서 처리 가능한 단위**로 묶는다(주문 처리 / 상품 조치 / 고객 응대 / 정산 확인). 상품 조치 하위 항목은 1-4의 그룹 이름과 일치시킬 것.
- `.todo-row`(base.html에 이미 있음) 재사용. 0건이면 "지금 할 일 없음" 초록 패널.
- 숫자 카드 9개 → 4개, **전부 클릭 가능**하게.
- 차트는 `<details open>`, 연동 상태(292px)는 `<details>` 기본 닫힘 — 설정 성격이라 매일 보는 화면에서 자리 차지할 이유 없음.

**딥링크 배선**: `HealthIssue`(health.py:24)에 `link: str = ""` 필드 하나 추가. 품절·마진붕괴·무판매는 루프 변수가 이미 `naver_product_id`를 들고 있는데 버리고 이름만 쓰는 중이라 링크 생성은 공짜. (`url_for`는 라이브러리에서 못 쓰므로 경로 문자열을 직접 넣을 것)

**속도**: `check_store_health(deep: bool = False)` 추가. `deep=False`면 네트워크를 타는 `sync_all(dry_run=True)` 대신 `data/product_sync_cache.json`을 읽는다. 홈에 항상 띄워도 안 느려진다. 무거운 진단은 `?deep=1` 버튼으로 유지.

### 차트 글자 크기 버그 (사용자가 별도 지적)

축 라벨(`20k`, `5,000`, 날짜)이 **화면이 넓을수록 커진다.** 차트가 좌표계 680단위를 창 너비에 맞춰 늘리는데 글자도 같이 늘어나기 때문.

| 창 너비 | 차트 폭 | 배율 | 축 라벨 실제 크기 |
|---|---|---|---|
| 좁을 때 | 958px | 1.41× | 14.8px |
| 넓은 모니터 | ~1900px | 2.79× | **약 29px** ← 사용자가 보는 화면 |

**고칠 것**: 글자 크기를 좌표계 단위(`font-size: 10.5`)로 고정하지 말고, 그릴 때 **배율을 나눠 항상 14px로 렌더**되게(`14 / 배율`). 배율 계산 코드는 툴팁 쪽(`var scale = svgRect.width / W`)에 이미 있으니 그대로 쓸 것. 범례(현재 12.5px)도 14px로 맞춰 추천 상품 영역(14px)과 통일. 창 크기 변경 시 재계산도 함께.

## 4단계 — 헬스체크 고도화 (신규 설계)

사용자 원문:

> "내가 원한 헬스체크는 내 스토어를 전체적으로 보고 좀 더 거시적인 관점에서 스토어를 체크해주는거였어. 전체적으로 매출이 감소하고있는지, 그럼 원인이 뭘로 추정되는지, 현재 트렌드가 어떤데 내가 지금 그걸 놓치고 있는건 아닌지 등등. 지금 버전은 단순히 내 스토어의 문제가 되는 부분만 부분적으로 보여주는 느낌."

현재 헬스체크는 개별 문제 나열이라 할 일 목록과 사실상 같다. **역할을 완전히 분리**한다.

```

   · 미등록 후보를 **틈새(바로 등록) / 리메이크(작업 필요)로 나눠서** 제시
```

### 정직성 설계 (중요)

`sales_orders.json`이 지금 **비어 있다.** 표본이 부족할 때 그럴듯한 분석을 지어내면 안 된다.

- 모든 원인은 **"추정"** 표시 + 근거 수치 동반
- 노출·클릭 데이터는 연동돼 있지 않으므로(비즈어드바이저 미연동, `performance.py` docstring 참고) "안 팔리는 이유"를 노출 부족/전환 부족으로 나누는 건 **불가능하다고 화면에 명시**. 지금 답할 수 있는 건 "팔 수 있는 상태였나 / 얼마나 팔렸나"까지다.

3. 탭·필터·**빈 상태(0건)**까지 눌러 확인
4. 실데이터가 비어 있으니 각 화면의 `샘플 데이터로 화면 확인` 버튼으로도 확인

### 특별히 확인할 것

- **일괄 발주의 "확인함" 게이트가 그대로 작동하는지** (실제 결제가 걸린 경로)
- 일괄 상품 액션의 dry-run 미리보기가 **실제로 아무것도 바꾸지 않는지**
- 이머니 부족 시 **서버가** 실제로 발주를 막는지 (버튼 disable만으로는 불충분)
- 상품 표에서 네이버 판매중지 상태가 눈에 띄게 표시되는지
- 헬스체크가 데이터 부족 시 지어내지 않고 "판단 불가"로 표시하는지
- **트랙 저장이 실제로 되는지** — 스캔 한 번 돌려서 새 후보에 트랙·월검색수가 남고, 같은 키워드의 리메이크 후보가 더는 사라지지 않는지
- 차트 축 글자가 **창 너비를 바꿔도** 14px로 유지되는지

### 자체점검(`__main__`) 대상

- `store_health.py` — 추세를 같은 일수로 비교하는지, 표본 부족 시 "판단 불가"를 반환하는지
- 후보 저장 변환 — 트랙·판정·월검색수가 보존되는지, `(키워드, 트랙)` 중복 제거가 두 트랙을 모두 남기는지
- `weekly.py` — 삭제된 메뉴명이 안 나오는지

## 9. 알려진 이슈 (이번 작업과 무관, 참고용)

- 네이버 커머스 API가 `GW.IP_NOT_ALLOWED`로 막힐 수 있음(공인 IP 변동) — 커머스API센터에서 IP 재등록 필요. **코드 문제 아님**
- 네이버 커머스 API `429 GW.RATE_LIMIT` 간헐 발생 — 짧은 시간에 여러 화면을 연속 새로고침하면 뜬다
- 부가세 조회가 `400 startDate는 전월자까지` 오류 — 당월 조회 불가가 API 사양
- 도매매 이머니 잔액 0원(2026-08-28 실측) — 실발주 전 충전 필요
- 골든레이시오가 전부 `inf` — 네이버쇼핑 API 종료로 상품수 조회 불가. **이번 범위 밖, 코드로 못 고침**
